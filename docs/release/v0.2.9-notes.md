**Type:** release-engineering and CI-hardening release. **No daemon code

## What is new since v0.2.8 (release infrastructure — no runtime change)

1. **F-02: the CLI release key is resolved only inside the protected
   environment (#132, issue #100).** `release.yml`'s `sign` job declares
   `environment: signing`, so a tag release (and the dry run) pauses for the
   environment's required reviewer before the key is read. A new structural
   guard rule `environment-scoped` plus the negative fixture
   `tests/ci/fixtures/release-workflow/bad-sign-no-environment.yml` fail CI if a
   `sign` job ever silently loses the gate. The stray, unprotected `release-cli`
   environment was deleted. Read the honest scope note in *Security posture*
   below: the **key itself is still repository-scoped**.
2. **OpenWrt e2e harness hardened (#134).** The lab starts the daemon
   explicitly when `rc.local` loses the boot race: proc-first readiness check,
   `setsid` fallback, 120 s re-poll. Diagnostics are collected **before**
   `lab down`, so a failure keeps its evidence. A forced-race rehearsal passed
   (439.97 s).
3. **CI network steps are bounded (#135).** `CURL_BOUNDED`/`APT_BOUNDED` plus
   per-job `timeout-minutes`: a stalled transfer now fails its step instead of
   hanging the gate. Measured: `sign + verify` 37m16s → 46–58 s; `integration`
   50+ min → ~3 min.
4. **S-005 govulncheck gates fail closed (#137).** With `-format json`
   govulncheck exits 0 even when it finds vulnerabilities, so the old gates
   keyed off the exit code could pass a broken or vulnerable scan (an empty
   stream was treated as clean, and `"${arr[@]:-}"` over an empty array matched
   an empty allowlist entry). The gates now share `scripts/lib/govuln-verdict.sh`
   and fail on: rc outside {0,3}, an unparsable or empty stream, a finding
   without a usable `osv` id, or any finding not in
   `packaging/govulncheck-allowlist.txt`. A new CI job runs the CLI-archive
   fixture suite; the clean-scan control must decode ≥1 `osv` record and 0
   `finding` records. Published v0.2.6–v0.2.8 artifacts were re-audited with raw
   `govulncheck -mode=binary` scans (9 artifacts, rc 0, **0 finding records**,
   228 `osv` records each, DB dated in the scan) — **nothing was masked**, so no
   advisory is needed for them.
5. **The apk build is codified, and a manifest proves it (#146).**
   `scripts/build-apk-release.sh` rebuilds the unsigned apk from committed
   inputs only: `git archive` of the commit, the committed overlay
   `packaging/apk-build/no-golang-host.patch` applied to a scratch copy, the
   committed SDK config, the SDK digest **read from `apk-sign.yml`** (so script
   and workflow cannot drift), the sha256-pinned official go1.27.4, and the
   zero-hash two-pass `PKG_MIRROR_HASH` derivation. It writes
   `build-manifest-<label>.json`, which `scripts/check-apk-build-manifest.sh`
   re-derives from the repository, and `release-pin-gate.sh` step 9 consumes
   (opt-in; the release run sets it together with `GATE_S005_CHECKS=1`).
6. **Post-tag pin and the step-9 recipe anchor (#148, #149).** The tag cannot
   contain its own hash, so the post-tag pin PR moves `PKG_SOURCE_VERSION` to
   the v0.2.9 tag commit and `PKG_MIRROR_HASH` to the value derived for it. Step
   9 was also fixed: it used to require `manifest.source.commit == tag`, which
   rejected the documented pin-commit flow; it now anchors the **recipe** to the
   tag (every recipe file except `openwrt/Makefile` byte-identical there; the
   tag's Makefile plus the manifest's stated pin and substitutions must match
   the compiled Makefile's executable lines) while the manifest stays
   self-consistent with the commit it records. Two new negatives cover
   post-tag recipe drift.

## Upgrade items (what changes for an operator)

- **Nothing in the daemon's behaviour.** v0.2.9 ships the v0.2.8 runtime; the
  apk version moves to `0.2.9-r1`, so an in-place `apk add` upgrade is
  `0.2.9-r1 > 0.2.8-r1`.
- The upgrade restarts the service through the package's post-install path.
  Measured on the fresh VM: **~0.4 s** in which *new* connections are dropped
  (the nftables hook stays installed while the NFQUEUE has no listener —
  fail-closed by design), then normal service. Plan package upgrades in a
  maintenance window if new connections must never be dropped; established
  traffic during the test was accepted (`accepted=219 dropped=0` at shutdown).
- The packaged source pin names the **v0.2.8 commit**: at the tag commit the
  Makefile still pins the previous release (a tag cannot contain its own hash).
  The runtime tree is identical between the two commits (the pin gate proves
  the empty runtime diff), and the post-tag pin PR (#148) points future rebuilds
  at `8e2ae79`.
- No configuration format change, no new required option, no migration.

## Security posture (F-02) — read this before quoting the release

- The `sign` job is **approval-gated**: `environment: signing` has required
  reviewer `88kbleirad`, `prevent_self_review=false`, deployment policies branch
  `main` + tag `v*`, and `can_admins_bypass=true` — so approval is a deliberate
  confirmation by the maintainer, **not** two-person control.
- The **CLI signing key `GH_RELEASE_SIGNING_KEY` is still repository-scoped**
  (`gh secret list` → repo scope; `gh secret list --env signing` → only
  `GH_RELEASE_APK_SIGNING_KEY`). The environment gate protects the *job*, not
  the key: any workflow could still reference the repo-scoped secret, which is
  why the guard rule only constrains `release.yml`'s `sign` job. **Do not
  describe the CLI key as environment-scoped.**
- Remaining work for real F-02: set the environment secret from the offline
  backup (or rotate), run a green dry run, then delete the repository-level
  copy — `docs/release/f02-environment-migration.md` §0/§3.
- The **apk** signing key *is* environment-scoped (`signing`), and the
  `apk-sign.yml` run reads it only through that scope.

## Known limitations

- **Release tags are annotated but unsigned** (`docs/trust/allowed_signers` is
  committed; tag signing is not enabled, and `GATE_TAG_SIGN_CHECK` stays
  opt-in). `v0.2.7` and `v0.2.8` shipped the same way.
- **Nothing protects `main` or the tags**: repository rulesets are empty and
  `main` has no branch protection, so anyone with write access can move a tag.
  Re-verify `git ls-remote --tags` before quoting an artifact.
- **`docs/release/` is English-only** by policy; there is no VI mirror.
- **arm64** is verified only under QEMU TCG (no hardware); the arm64 CLI archive
  is cross-built and its ELF/static properties are checked in CI.
- The apk is **not** covered by `checksums.txt` (separate key domain); use
  `scripts/verify-release-assets.sh` for a whole-release check.
- Step 9 in the **tag's own** `scripts/release-pin-gate.sh` still compares the
  manifest commit with the tag; the fix (#149) is on `main` after the tag. The
  release artifact was therefore built at the tag commit, and the gate above
  was run from `main`. Rebuilds at the pin commit need `main` ≥ `6b19d01`.
- PR **#150** (NAT test readiness: wait for `nat_enabled=true` + `NFQUEUE
  bound` instead of a fixed sleep) is open, CI 16/16 green; it changes tests
  only and is not part of the artifacts.
