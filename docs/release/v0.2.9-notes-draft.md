## What changed in CI/tooling (not runtime)

### F-02 (issue #100) — the CLI signing key is approval-gated again

- `release.yml`'s `sign` job declares `environment: signing` (required reviewer
  `88kbleirad`; deployment policies `main` branch + `v*` tag), so a tag release —
  and the dry run — pause for approval before `GH_RELEASE_SIGNING_KEY` is
  resolved (#132). Observed during the window: dry run `45163234154` stopped at
  `sign release artifacts (protected environment)` with status `waiting`.
- New structural guard rule `environment-scoped` plus the
  `bad-sign-no-environment.yml` negative fixture: a `sign` job that silently loses
  the environment fails CI (the #125 regression class). `secret-scope` still
  confines the key to `sign` in every scanned workflow. (Verified on `main`; see
  "Verification performed".)
- The stray, unprotected, secret-less `release-cli` environment was deleted;
  repository environments are `github-pages` and `signing` (recorded observation,
  not re-verified here).
- **Still open in #100, and the reason the gate is not yet fail-closed:** an
  environment declaration does not pin the key's provenance. GitHub resolves an
  environment secret in preference to a same-named repository secret, but when
  the environment does not define the name it silently falls back to the
  repository-level copy. Whether the key now lives in `signing` is exactly the
  unknown in §C: until the environment secret exists *and* the repository-level
  copy is removed, a tag run is approved **and then** signs with the
  repository-scoped key. See `docs/release/f02-environment-migration.md` §0.3.
- Also worth stating plainly: `signing` has `can_admins_bypass: true` and
  `prevent_self_review: false`, so the approval is deliberate confirmation, not
  two-person control.

### e2e harness — an rc.local boot race can no longer fail the gate (#134)

- `scripts/openwrt-e2e.sh` (v4) gained the explicit daemon start that
  `openwrt-e2e-v6.sh` always had: readiness polls
  `/proc/net/netfilter/nfnetlink_queue` first (authoritative — a bound queue has
  a non-zero peer portid), then the `NFQUEUE bound` log line, and after 300 s
  starts the daemon itself (`setsid ... < /dev/null &`, busybox has no `nohup`)
  before re-polling for 120 s. Proven in the PR's forced-race rehearsal
  (autostart removed from a provisioned image): the run logged
  `daemon not ready after 300s; starting it explicitly` and still passed both
  DROP/ACCEPT controls (439.97 s).
- `scripts/e2e-runner.sh` collects `failure-diagnostics.txt` **before** `lab down`
  (the teardown-first order produced an artifact with an empty serial tail and no
  guest state) and adds bounded guest probes: daemon log tail,
  `logread -e goshisen`, `dmesg`, `pidof goshisen` + queue kmods,
  `nfnetlink_queue`, and the `goshisen` nft table. A deliberate-failure run
  produced 3585 B of guest evidence where the old order produced 853 B of nothing.

### CI — network steps are bounded (#135)

- Workflow-level `CURL_BOUNDED` (`--connect-timeout 15 --max-time 300 --retry 3
  --retry-delay 5 --retry-all-errors`) wraps the pinned syft download;
  `APT_BOUNDED` (`-o Acquire::http::Timeout=30 -o Acquire::https::Timeout=30
  -o Acquire::Retries=3`) wraps every `apt-get update/install`.
- Job-level `timeout-minutes` on every job that touches the network or a
  privileged lab (`build` 20, `arm64` 20, `robustness` 30, `package` 30,
  `verify-signatures` 30, `openwrt-integration` 45, `openwrt-integration-v6` 60,
  `integration` 30; `release.yml` already had 15/45/30).
- Two real hangs measured before the fix: `sign + verify release artifacts`
  37m16s (syft download) and `integration` 50+ min (`apt-get update`). After it:
  46–58 s and 2m59s/3m13s respectively, all jobs green on both runs. These are
  PR #135's figures; the v0.2.9 tag run's timings are `<fill from the run>`.

### S-005 govulncheck gates can no longer fail open (security fix)

- The two signing-path gates — `scripts/check-apk-payload-govuln.sh` (apk
  payload) and `scripts/check-cli-archive-govuln.sh` (CLI archives) — each
  carried the same verdict code, and that copy compared
  `"${findings[@]:-}"` against `"${allowed[@]:-}"`; over an EMPTY array that
  expands to one empty word, so `[ "" = "" ]` "matched" and a scan with no
  parsable finding IDs printed `…-GOVULN-GATE-PASS`, reported as "findings are
  allowlisted". Measured against the pre-fix scripts with a stubbed
  `govulncheck`: exit 3 with an empty stream, exit 3 with a finding entry that
  carried no OSV id, and exit 137 (SIGKILL) all PASSed; the fixed gates fail
  closed on all three.
- Both gates now source one implementation, `scripts/lib/govuln-verdict.sh`,
  which keys the verdict off the parsed stream (govulncheck exits 0 under
  `-format json` even when it finds vulnerabilities — `cmd/govulncheck/doc.go`
  in v1.9.0 — so findings arrive on rc 0) and fails closed on an unparsable or
  empty stream, a finding entry without an OSV id, an un-allowlisted finding,
  a missing/non-executable `govulncheck`, and any exit code other than 0/3.
  Findings are printed whether the gate passes or fails.
- The stub outcome matrix in `tests/ci/check-apk-payload-govuln-test.sh` pins
  the rule set; both gate tests keep their real-tool fixtures (current
  toolchain passes, old-Go fixture fails with the blocked IDs, allowlisted IDs
  pass and are reported) and pass locally against govulncheck v1.9.0.
- The clean-control PASS is now pinned to the reason, not just the exit code:
  `tests/ci/lib/govuln-clean-stream.sh` requires the current-toolchain scan's
  JSON to carry at least one `osv` record and zero `finding` records (measured:
  `osv=228 findings=0` for the payload and the archive). The CLI gate's fixtures
  — unrun in CI until now — run as their own job,
  `cli-archive-govuln-gate (S-005)`.

### apk build — the recipe, manifest and gate are committed (#146)

- The v0.2.6–v0.2.8 apks were built from a *local, uncommitted* recipe copy, so
  "built from the repo" was not reproducible by anyone else. Now
  `packaging/apk-build/no-golang-host.patch` is that single recipe change as a
  committed patch (applied to a scratch copy of `openwrt/Makefile`, never the
  working tree), `packaging/apk-build/sdk-x86_64.config` is the SDK config
  fragment the published v0.2.8 apk was built with, and
  `packaging/go-toolchain.env` pins the official go1.27.4 tarball and `bin/go`
  sha256.
- `scripts/build-apk-release.sh` builds the unsigned package from committed
  inputs only (`git archive` at `--commit`; digest-pinned SDK image; verified Go
  tarball/`bin/go` hashes; `PKG_MIRROR_HASH` derived or verified;
  unsignedness asserted inside the container with `apk verify` →
  `UNTRUSTED signature`) and writes `build-manifest-<label>.json`.
  `scripts/check-apk-build-manifest.sh` re-derives every claim in that manifest
  from the commit; `scripts/release-pin-gate.sh` gained opt-in step 9
  (`--manifest` / `GATE_MANIFEST`) so a release run can tie the published apk to
  the committed recipe.
- CI does not build the apk; `apk-build-manifest-gate (F-01)` runs
  `tests/ci/apk-build-manifest-test.sh`: generated fixtures, every negative case
  rejected for a named reason, plus the pin-gate step 9 integration against a
  scratch tag. The valid case is a real cross-check — the fixtures replay the
  recipe with `patch(1)`+`sed(1)` while the checker replays it with
  `git apply`+python.
- Proof runs are recorded in `docs/release/v0.2.9-apk-build-recipe.md`: two
  independent builds at one commit produced identical apk (`fa3b9530...`,
  3,286,016 B) and payload (`ba8183b1...`) hashes (§7); the same script
  rebuilding the v0.2.8 inputs reproduced the published *pre-signing* apk
  byte-for-byte (`b97f0da4...`, `cmp` identical, §8); a fresh no-daemon guest
  installed the package, survived SIGKILL, upgraded over the signed v0.2.8 apk
  (21/21 probes blocked, 0 fail-open) and removed cleanly (§9). All of it is
  evidence about the **recipe at the branch tip**, not about a v0.2.9 artifact.
- One v0.2.8 note has to go: "the two apk hashes differ only by the appended apk
  v3 signature block" is a size description, not a byte layout — the first
  3,286,014 bytes of the published signed apk are not a prefix of the unsigned
  artifact (§8, second note).

## Reproduction

Aim, not evidence, until the build runs: no v0.2.9 apk exists yet. Target
procedure — committed since #146, so anyone can repeat it:

```sh
scripts/build-apk-release.sh --commit <v0.2.9 pin commit> \
  --go-root <verified go1.27.4> --label A --out <dir> --work <scratch-A> --canonical-name
scripts/build-apk-release.sh --commit <v0.2.9 pin commit> \
  --go-root <verified go1.27.4> --label B --out <dir> --work <scratch-B>
scripts/check-apk-build-manifest.sh --manifest <dir>/build-manifest-A.json \
  --compare <dir>/build-manifest-B.json --apk <dir>/goshisen-0.2.9-r1.apk \
  --payload <extracted usr/sbin/goshisen>
```

The script `git archive`s the commit, applies the committed overlay
`packaging/apk-build/no-golang-host.patch` to a scratch copy (never the working
tree's `openwrt/Makefile`), folds in `packaging/apk-build/sdk-x86_64.config`,
verifies the pinned go1.27.4 tarball/`bin/go` hashes, and uses the SDK digest
pinned in `apk-sign.yml`. `scripts/release-pin-gate.sh --manifest
<dir>/build-manifest-A.json` (or `GATE_MANIFEST=`) runs the check as step 9, so
the release run can tie the published apk to the committed recipe; the step is
opt-in, so no existing caller changes.

Do **not** publish a "clean SDK build" claim: the toolchain comes from outside
the SDK tree, and the mirror hash is toolchain-specific. The precise guarantee
to state, if the A/B check passes, is **identical hashes on repeated builds of
the same pin with the same toolchain, SDK image and feed commits** — not across
toolchains or SDK trees. CLI archives: `ci.yml`'s `package` job enforces a
byte-identical rebuild (`cmp`); paste the tag-run result instead of asserting it.

## Known limitations

- The CLI key's scope is **unverified** (see §C). The approval gate is live; the
  scope reduction is complete only once the `signing` environment lists
  `GH_RELEASE_SIGNING_KEY` *and* the repository-level copy is deleted — until
  then a job that declares the environment is approved and then signs with the
  repository-level secret, and any workflow in the repo can still read that copy.
  Fill in: `<env secret present? yes/no — from gh secret list --env signing>`.
- `signing` is shared with `apk-sign.yml`: a job declaring that environment can
  read both keys (documented in `docs/release/f02-environment-migration.md`
  §0.2). `can_admins_bypass` is `true` and `prevent_self_review` is `false` on
  `signing`, so the approval is deliberate confirmation rather than two-person
  control (§0.3).
- `docs-site/translations/vi/docs/release-checklist.md` predates the F-02 section
  and is shorter than the English checklist (pre-existing drift, tracked
  separately). `docs/release/**` is deliberately not translated (docs-site
  policy: release docs stay English).
- The build manifest ties the apk to the committed recipe; it does **not** prove
  the build ran on the tag commit (`--commit`/`--tag` is the caller's claim,
  checked against the manifest's `source.commit`), and the pin gate's manifest
  step is opt-in — the release run has to pass `--manifest`/`GATE_MANIFEST` for
  it to apply (`docs/release/release-pin-gate.md`, step 9).
