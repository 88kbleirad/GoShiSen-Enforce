# GoShiSen-Enforce — v0.2.1 Release Notes (draft)

Status: draft. Only claims backed by executed evidence are stated. VM
evidence is in `/data/phase14-artifacts/` (sha256 per artifact), from
builds of pushed commits only.

## What this release is

v0.2.1 is a hardening + policy-control release on top of the published
v0.2.0. It adds the opt-in flow-offload policy (`offload_policy`), a
pre-firewall fail-closed boot guard (`goshisen-boot`), reproducible apk
container builds, and verification of stateful IPv6 conntrack delivery on
the supported kernel.

## New since v0.2.0

- **Flow-offload policy** (Issue #6): opt-in, non-silent response to a
  detected enforcement gap (established flows bypass the queue when
  nftables flow offloading is active):
  - `warn` (default): WARN log + `goshisen_flow_offload_active` gauge;
    enforcement continues, readiness unaffected.
  - `refuse`: startup fails **before** installing the hook when
    offloading is detected (fail-closed by absence; system left
    untouched). VM-verified: the daemon exits with a clear error and
    forwarded traffic stays blocked until offloading is disabled or the
    policy is changed.
  - `readiness`: the daemon keeps enforcing but holds `/readyz` at 503
    while offloading is active; the 10 s watcher drops readiness if
    offloading appears later and restores it once the ruleset is clean.
    VM-verified: `GET /readyz` → HTTP 503 with offload active; readiness
    recovers ≤2 s after offload disable.
  - The daemon never modifies the user's firewall.
  - Config surface: `offload_policy` in the daemon YAML,
    `GOSHISEN_OFFLOAD_POLICY`, and OpenWrt UCI
    `goshisen.main.offload_policy` (init-script validated; invalid
    values rejected before the daemon starts).
- **Boot guard** (Issue #4): `goshisen-boot` (START=12, before firewall4
  S19) installs a forward default-drop chain for IPv4+IPv6 (inet family,
  no input/output chains, no accept/bypass) when the service is enabled,
  closing the measured fail-open window. The daemon's Install replaces it
  atomically; `hook cleanup`/`apk del` remove it. Reboot matrix
  (5 reboots, LAN→WAN marker probes every ~50 ms): forwarded-before-
  enforcement = 0 in every run; post-enforcement traffic flows
  (positive control). `apk del` removes the guard table and rc.d links;
  `goshisen hook cleanup` restores fw4-only forwarding.
- **Reproducible apk**: two clean SDK builds from the same pinned commit
  produce a byte-identical `.apk`
  (`sha256 264b2ac2…`), not just a reproducible binary. (This
  supersedes the v0.2.0 note that the container was timestamp-dependent;
  the SDK's fixed `TAR_TIMESTAMP` + `--sort=name` pack yields a stable
  container.)
- **Stateful IPv6 conntrack delivery verified on kernel 6.12.112**
  (Issue #5): queue 101 receives the same `NFQA_CFG_F_CONNTRACK`
  configuration as queue 100; live daemon metrics show IPv6 TCP SYNs are
  classified NEW (not INVALID), proving the kernel attaches CT attributes
  to IPv6 packets on this kernel. The v0.2.0 INVALID-fallback limitation
  is therefore kernel-dependent and does not apply to OpenWrt 25.12.6's
  kernel for the NEW path.

## Known limitations (updated)

- **Flow offloading is detected, not disabled.** `offload_policy`
  controls the daemon's response; it never disables the user's
  offloading. Recommended: keep `flow_offloading` disabled on routers
  that rely on GoShiSen enforcement, or use `offload_policy` to make the
  gap visible.
- **Detection latency**: the offload watcher polls roughly every 10 s;
  observed latency in the VM was ≤2–4 s in both directions (firewall
  reload triggers immediate nft reads).
- **`refuse` mode outage behavior**: with offloading enabled,
  `offload_policy=refuse` makes the daemon exit at startup, so traffic
  stays blocked — this looks like an outage. Documented recovery:
  disable offloading (or set `offload_policy` to `warn`/`readiness`),
  then (re)start the daemon.
- **Stateful IPv6 end-to-end (ESTABLISHED replies)**: NEW classification
  is verified on kernel 6.12.112, but a full v6 handshake with reply
  traffic could not be exercised in the lab (slirp WAN has no IPv6
  peer). The engine's ESTABLISHED/RELATED path is family-agnostic and
  covered by the v4 integration suite.
- **Impact proof (bypass)**: the lab's kernel flowtable did not actually
  offload flows (flowtable counter 0), so the offload bypass itself was
  not directly observable; detection and policy responses are fully
  verified.
