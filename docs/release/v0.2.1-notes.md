# GoShiSen-Enforce — v0.2.1 Release Notes (draft)

Status: draft. Only claims backed by executed evidence are stated.

## What this release is

v0.2.1 is a hardening + policy-control release on top of the published
v0.2.0. It adds the opt-in flow-offload policy (`offload_policy`), a
pre-firewall fail-closed boot guard (`goshisen-boot`), reproducible apk
container builds, atomic durable policy publishes, allocation-free hot
path performance, and verified stateful IPv6 end-to-end coverage.

## New since v0.2.0

### Flow-offload policy (Issue #6, PR #14)
`offload_policy` (default `warn`):
- `warn`: WARN log + `goshisen_flow_offload_active` gauge; enforcement
  continues, readiness unaffected. VM-verified.
- `refuse`: startup fails **before** installing the hook when offloading
  is detected (fail-closed by absence, system untouched). VM-verified:
  the daemon exits with a clear error; forwarded traffic stays blocked
  until offloading is disabled or the mode is changed.
- `readiness`: daemon keeps enforcing but holds `/readyz` at `503
  not_ready` while offloading is active; readiness recovers (≤2 s in
  the VM) once the ruleset is clean. VM-verified.
- The daemon never modifies the user's firewall.
- Config surface: daemon YAML `offload_policy`, env
  `GOSHISEN_OFFLOAD_POLICY`, OpenWrt UCI `goshisen.main.offload_policy`
  (invalid values rejected by the init script before the daemon runs).

### Pre-firewall fail-closed boot guard (Issue #4, PR #13)
`goshisen-boot` (START=12, before firewall4 S19) installs a forward
default-drop chain for IPv4+IPv6 (inet family; no input/output chains, no
accept/bypass) when the service is enabled — closing the measured
fail-open window. The daemon's hook Install replaces the guard table
atomically; the guard is a no-op when the service is disabled. `goshisen
hook cleanup` / `apk del` remove the table.

### Atomic durable policy publishes (Phase 15)
SIGHUP file reload and REST API apply/activate now share one publish
pipeline: compile → next version from the durable store → durable write
(policy file then active pointer, both fsync'd) → `King` snapshot swap,
all under one process-wide mutation lock. Any failure keeps the previous
policy in both the store and the live ruleset; a daemon restart after a
mid-publish kill never activates a torn version (restart reads the
*active* pointer). New observability: `goshisen_policy_updates_total
{outcome="success"|"failure"|"conflict"}`. `policy dry-run` (CLI)
previews the exact publish read-only.

### Performance (Phase 16)
Zero-allocation hot path: packed 5-tuple accepted-set key (no `fmt`/
string), state bitmask + value ports in `Rule`, single-lock fixed-array
packet metrics, pooled verdict buffer, inlined attribute parse.
Measured on the same machine (3 runs, median; see
`docs/design/performance-phase.md` + `evidence/perf-prompt03/`):
- `King.Process` NEW accept 2510 → 95.6 ns (−96%); established
  1081 → 50.7 ns (−95%); tupleKey 664 → 4.1 ns (−99%).
- pipeline e2e NEW accept 1129 → 253 ns (−78%); established reply
  634 → 193 ns (−70%); default-drop 668 → 206 ns (−69%); metrics-only
  86.5 → 15.8 ns (−82%); latency p50 1.04 → 0.31 µs; p95
  1.72 → 0.31 µs; p99 2.69 → 0.48 µs; **0 allocations per packet**
  (was 15–16).
Semantics unchanged: stateful reply canonicalization pinned by
`tuplekey_test.go` (v4/v6); `go test -race ./...` + `make check` green;
verdict wire format unchanged (`TestVerdictMessageGolden`).

### Stateful IPv6 verified on OpenWrt 25.12.6 (kernel 6.12.112)
Dual-bridge QEMU lab with real IPv6 LAN/WAN peers (PR #13+#14+#15
merge `f5f211a`, package r4): paired positive/negative controls per
family — deny blocks, allow (NEW) passes, established-reply passes —
for both v4 and v6 on r2 baseline, r4 post-upgrade, and r2
post-rollback (all PASS). IPv6 ESTABLISHED-reply is exercised with real
v6 peers; metrics show `state="established"` accepts.

## Upgrade / rollback (verified on the target)

- Upgrade v0.2.0 (r2) → r4: binary swapped; `goshisen-boot` added; UCI
  conffile preserved (packaged default written as `policy.yaml.apk-new`);
  no fail-open window during `apk add` (old process keeps its inode; a
  restart picks up the new binary). Old r2-era UCI (no `offload_policy`)
  loads fine on r4 and defaults to `warn`.
- Init ordering: `S12goshisen-boot` → `S19firewall` → `S90goshisen`;
  `K10*` teardown links present.
- Reload failure: a malformed policy via SIGHUP is rejected
  (`policy reload rejected; keeping previous policy`); the previous
  policy stays active and traffic continues.
- Daemon crash: `kill -9` → procd respawns; during the down window
  forwarding is fail-closed (queue unbound → kernel drops); after
  respawn policy and queues are restored and controls pass.
- Rollback r4 → r2: binary sha returns to r2; service starts; all
  controls still pass. **Caveat:** the downgrade leaves dangling
  `S12goshisen-boot`/`K10goshisen-boot` rc.d symlinks (r2 does not ship
  the guard); run `/etc/init.d/goshisen-boot disable` before downgrading.

## Known limitations (verified)

- Flow offloading is detected, not disabled. `offload_policy` controls
  the daemon's response; it never disables the user's offloading.
  Recommended: keep `flow_offloading` disabled on routers that rely on
  GoShiSen enforcement, or use `offload_policy` to make the gap visible.
- Detection latency: the offload watcher polls roughly every 10 s;
  observed latency in the VM was ≤2–4 s in both directions.
- `refuse` mode behavior: with offloading enabled, `offload_policy=
  refuse` makes the daemon exit at startup, so traffic stays blocked —
  this looks like an outage. Recovery: disable offloading (or set
  `warn`/`readiness`), then (re)start the daemon.
- Flowtable offload impact is not directly observable in the TCG lab
  (flowtable counter 0); detection and policy responses are fully
  verified.
