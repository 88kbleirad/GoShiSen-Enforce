# GoShiSen-Enforce v0.2.3 — Release Notes (draft)

**Status:** draft for v0.2.3. **Date:** 2026-11-15.
**This is a packaging/signing release: no runtime source change since
v0.2.2.**

## What is in v0.2.3

- First release whose OpenWrt package (`0.2.3-r1`) is **production-signed**
  (apk v3 embedded signature, anchor
  `keys/goshisen-apk.pub.pem`, fingerprint
  `542bb7ae9058fee9b4d37ed30b0af44f234ea7cb8866daa1ffc71a7bc37c839d`).
  Previous published APK (v0.2.0's `0.2.0-r2`) was **unsigned**;
  v0.2.1 and v0.2.2 published no APK asset.
- CLI release again signs archives with the production Ed25519 key
  (signatures + provenance + SBOM), as v0.2.2.
- Package daemon stamp reports `0.2.3` (package version); the runtime
  source is identical to v0.2.2 (`c5de6e8`) — same source, different
  stamp. `git diff c5de6e8 v0.2.3 -- internal cmd pkg go.mod go.sum`
  is empty (verified before release).
- The CLI release key (`GH_RELEASE_SIGNING_KEY`) and the APK signing key
  (`GH_RELEASE_APK_SIGNING_KEY`) are different and never interchanged.

## Verifying and installing the signed package

APK public trust anchor (full SHA-256 of DER SPKI):
`542bb7ae9058fee9b4d37ed30b0af44f234ea7cb8866daa1ffc71a7bc37c839d`.
Cross-check this fingerprint from a second source (e.g. the repository
`keys/goshisen-apk.pub.pem` + the custody record in
`docs/release/apk-signing-key-custody.md`).

Install the anchor into the OpenWrt trust store and install the package
**without** `--allow-untrusted`:

```sh
# on the router/VM (as root)
mkdir -p /etc/apk/keys
# fetch the anchor (or copy from a trusted medium)
wget -O /etc/apk/keys/goshisen-apk.pub.pem \
  https://raw.githubusercontent.com/88kbleirad/GoShiSen-Enforce/v0.2.3/keys/goshisen-apk.pub.pem
openssl pkey -pubin -in /etc/apk/keys/goshisen-apk.pub.pem -outform DER | sha256sum
# must print: 542bb7ae9058fee9b4d37ed30b0af44f234ea7cb8866daa1ffc71a7bc37c839d

# verify the package signature with apk (expected: OK)
apk verify --keys-dir /etc/apk/keys /path/to/goshisen-0.2.3-r1.apk

# install (signature verified by apk; no --allow-untrusted)
apk add /path/to/goshisen-0.2.3-r1.apk

# check the installed binary + its checksum
apk list --installed | grep goshisen
sha256sum /usr/sbin/goshisen
/usr/sbin/goshisen --version   # => goshisen 0.2.3
```

The release's `checksums.txt` lists the CLI archive hashes (signed by the
release step). The **signed APK** asset is
`goshisen-0.2.3-r1.apk` with sha256
`948e2e1de454c159bed81bfe845bad160dcf9454238b532b2a87f2e335b0cc6a`
(production-signed; gate provenance records it). The pre-signing apk
(built from the same commit, same recipe) has sha256
`d0a66f461129e89b9eadb97e0a057efa24adaf656799bf9853c3cfe8c7ef12d9`;
the difference between the two is exactly the appended apk v3 signature
(control block + signature), which apk-tools verifies. Both contain the
same daemon binary: sha256
`57aef2cf558d80ed8d51c9e7f746021e101cde7a9427fc6432eaab69735b89c0`
(static x86-64 ELF, `--version` → `goshisen 0.2.3`).

**Reproducibility statement:** the apk container embeds a build timestamp
(`version.date`, from the source archive's commit time), so two apk
builds at different wall-clock times produce different *container* sha256
even for byte-identical payloads. The dry-run for this release produced
identical apk sha256 on two clean back-to-back SDK builds (both
`d0a66f46…`) because they shared the same source archive and build
environment (`SOURCE_DATE_EPOCH`-style fixed mtime from the pinned commit
`c5de6e8` → `1794633465`). Guaranteed: two clean builds from the same
pin in the same official SDK produce the same container hash today.
Not guaranteed: byte-identity across different toolchains, times, or
non-official environments (the instabox SDK produced a different tarball
hash, `2ed64a1e…`, documented in PR #39).

## Which public key is which

- **APK anchor** (used to verify the package): `keys/goshisen-apk.pub.pem`
  — an EC (P-256) public key, DER-SPKI SHA-256 fingerprint
  `542bb7ae9058fee9b4d37ed30b0af44f234ea7cb8866daa1ffc71a7bc37c839d`.
  Install it at `/etc/apk/keys/goshisen-apk.pub.pem` on OpenWrt.
- **CLI release key** (used to verify the tarballs/checksums/SBOM):
  the `public_key.pem` asset attached to this release — an Ed25519
  public key produced by the release signing step. It is **NOT** the APK
  anchor and cannot be used to verify the package; the two keys are
  distinct and never interchanged (verified by the signing gate).

## Known limitations

- **IPv6 queue 101 (queued, fail-closed):** IPv6 forwarded TCP/UDP is
  queued to queue 101 (queue 100 + 1) via the `inet goshisen` hook; the
  daemon binds a dedicated AF_INET6 socket there. Verified on a fresh VM
  with the signed apk: queue 101 bound (non-zero portid), IPv6 forward
  under the packaged DROP policy is BLOCKED (curl 28; zero v6 requests
  reached the destination; daemon drop counter advances), with an IPv4
  positive control (HTTP 200) in the same topology.
- **Stateful IPv6 (issue #5):** stateful IPv6 ACCEPT relies on kernel
  conntrack CT-attribute delivery; when unavailable, affected traffic is
  INVALID → DROP (fail-closed). Stateless IPv6 ACCEPT is verified.
- **Other architectures (issue #7):** x86_64 and aarch64 (armsr/armv8,
  QEMU TCG) are verified; other OpenWrt targets are untested.
- **LuCI (issue #8):** a LuCI frontend is proposed (design doc) but not
  implemented.
- **Package pin vs release tag (issue #9):** the package pins the daemon
  source SHA (`c5de6e8`, v0.2.2) rather than the tag itself — deliberate
  (self-referential pin avoided); see the v0.2.3 proposal.
- The daemon binary's `--version` prints `0.2.3` (no `-r1` suffix; the
  package release suffix is an apk concept).
- QEMU TCG emulation only for aarch64 (no physical hardware claim);
  flowtable offload hit counters are TCG-zero (bypass impact not
  observable in the lab).
- **Boot-guard:** the package ships `goshisen-boot` (START=12) which
  drops forwarded traffic in the app-owned table before the daemon
  replaces it — the pre-daemon window is fail-closed (measured ~170ms
  in v0.2.1; unchanged). `apk del` runs the hook cleanup.
- **apk checksum:** the signed apk's sha256 is recorded in this body and
  in the signing gate provenance; `checksums.txt` intentionally contains
  only the CLI archive hashes (it carries a detached release signature
  that would be invalidated by editing).
