## 2. 0.2.6-r1 and 0.2.7 failure states — PASS → BLOCKED

Installed the public signed apk, enabled the service
(`uci set goshisen.main.enabled='1'`, `api_port='8080'`,
`metrics_port='9099'`), then forced each failure state. Result for both
the 0.2.6-r1 release and the 0.2.7 test build:

| State | IPv4 | IPv6 | hook queue rule counter | `/proc/net/netfilter/nfnetlink_queue` | daemon |
| --- | --- | --- | --- | --- | --- |
| baseline, no goshisen | 200 | 200 | no table | empty | none |
| daemon running, ACCEPT policy | 200 | 200 | advances | `100 …` / `101 …` | bound |
| invalid `api_port 'abc'` → abort | blocked | blocked | **advances** | **empty** | PID=none |
| service disabled (`enabled=0`) | blocked | blocked | advances | empty | PID=none |
| `/etc/config/goshisen` missing | blocked | blocked | advances | empty | PID=none |
| daemon killed (SIGKILL), hook left, no respawn | blocked | blocked | advances | empty | PID=none |

Queue-rule packet counters (v4 = v6, one blocked probe per family state):
`20 → 26 → 32 → 38 → 44` on 0.2.6-r1 and `10 → 16 → 22 → 28 → 34` on
0.2.7 — measured, so the packets the LAN client sends **reach the
goshisen queue rule** and are then dropped by the kernel because no
userspace listener is bound on that queue (`nfnetlink_queue` has no line
for queue 100/101). The `inet goshisen` table for the invalid-port state
(0.2.7), verbatim:

```nft
table inet goshisen { # handle 12
	chain forward { # handle 1
		type filter hook forward priority filter + 1; policy accept;
		ct state { invalid, established, related, new, untracked } counter packets 16 bytes 960
		meta nfproto ipv4 meta l4proto { tcp, udp } counter packets 16 bytes 960 queue to 100
		meta nfproto ipv6 meta l4proto { tcp, udp } counter packets 16 bytes 960 queue to 101
	}
}
```

`logread` (this run):

```
daemon.err goshisen: api_port 'abc' is not a port (0-65535); refusing to start
daemon.warn goshisen: api_port is not set; treating it as 0 (listener disabled)
daemon.err goshisen[...]: msg="queue stopped; hook left in place (fail-closed)"
```

States in which the daemon **never** started (service disabled from the
package's own default, config missing) have only the boot guard's chain —
`type filter hook forward priority filter; policy drop;` with **no**
counter statement and no queue rule; those states are "blocked by the
guard's policy drop", which the table dump above distinguishes from the
queue-drop states.

## 3. Daemon death: bounded transient, never fail-open

procd respawn intact (`procd_set_param respawn 0` = unlimited retries):
a fast probe stream at ~0.15 s cadence across `kill -9` recorded
**1605 probes, 1603 passed, 2 blocked** — the daemon was back before the
next probe, and no deny probe ever passed. With the procd instance
removed first (`ubus call service delete`), the state is persistent:
blocked, hook left, no listener (row above).

## 4. Upgrade scenarios (i)-(v) — real file-level upgrade, dual streams

Action per variant: apply the UCI state, replace the files the 0.2.7 apk
installs (binary + init script + `.apk-new` config), `restart`, with a
continuous probe stream across the whole window (~24 s at ~0.15 s
cadence, `curl -m 1`).

**Deny stream** — policy `default_action: DROP`; no probe may ever pass:

| Scenario | UCI before | probes | pass | blocked |
| --- | --- | --- | --- | --- |
| (i) shipped config untouched | `api_port '0'`, `metrics_port '0'` | 22 | **0** | 22 |
| (ii) user enabled | `api_port '8080'`, `metrics_port '9099'` | 22 | **0** | 22 |
| (iii) options absent | both deleted | 22 | **0** | 22 |
| (iv) options empty | `api_port ''`, `metrics_port ''` | 22 | **0** | 22 |
| (v) config missing | `/etc/config/goshisen` removed | 24 | **0** | 24 |

**Allow stream** — policy `default_action: ACCEPT`; blocked probes are the
availability gap:

| Scenario | probes | pass | blocked (gap) | gap window |
| --- | --- | --- | --- | --- |
| (i) shipped config | 142 | 141 | **1** | 04:07:19 (1 s) |
| (ii) user-enabled ports | 143 | 142 | **1** | 04:07:52 (1 s) |
| (iii) options absent | 141 | 140 | **1** | 04:08:25 (1 s) |
| (iv) options empty | 141 | 140 | **1** | 04:08:57 (1 s) |
| (v) config missing | 51 | 32 | **19** | 04:09:30–04:09:51 |

Interpretation:

- The restart gap is **one probe wide (~1 s)** in the four scenarios where
  the service comes back up, consistent with
  `queue stopped; hook left in place (fail-closed)` → the kernel drops
  queued packets while no listener is bound → daemon rebinds. Deny
  traffic never passes during that gap.
- Scenario (v) is the exception by design: with no config the init script
  refuses to start (`service is disabled`), the hook stays and forwarding
  remains blocked until the operator restores the config or clears the
  hook (`goshisen hook cleanup`); the allow stream shows 19 blocked
  probes = still blocked after the window.
- **Scenario (i) is the packaged behavior change:** on ≤ v0.2.6 the
  packaged `'0'` values were ignored and both loopback listeners ran; on
  v0.2.7 they disable. A one-time upgrade notice is proposed in the item 2
  PR (`openwrt/Makefile` postinst marker + init `start()` `daemon.warn`),
  not merged.
