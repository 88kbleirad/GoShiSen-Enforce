## User-visible changes

### 1. `0` now disables the HTTP listeners at every layer (the v0.2.6 docs-gap)

On every published release ≤ v0.2.6 a value of `0` for `api_port` /
`metrics_port` was **ignored** when given in YAML, in UCI
(`option api_port '0'`), or as `--api-port 0` / `--metrics-port 0` —
only `GOSHISEN_API_PORT=0` / `GOSHISEN_METRICS_PORT=0` disabled. The
daemon therefore listened on `127.0.0.1:8080` and `127.0.0.1:9090` by
default whenever it ran (measured, see `docs/release/listener-defaults-evidence-20261120.md`).

In v0.2.7 the presence-tracking fix (PR #89, on `main` since the
v0.2.6 tag) is in a **published artifact for the first time**:

- config file `api_port: 0` / `metrics_port: 0` disables;
- `--api-port 0` / `--metrics-port 0` disables;
- `GOSHISEN_API_PORT=0` / `GOSHISEN_METRICS_PORT=0` disables (unchanged);
- an **unset** port keeps the documented default (`127.0.0.1:8080`
  API, `127.0.0.1:9090` metrics);
- an empty environment value (`GOSHISEN_API_PORT=`) is unset;
- YAML `api_port: ""` is a config error (the daemon refuses to start);
- precedence remains `defaults < file < env < flags`; a flag `0`
  overrides a file value.

**OpenWrt upgrade effect:** a router whose `/etc/config/goshisen` kept
the packaged `option api_port '0'` / `option metrics_port '0'` (both
listeners were actually listening on ≤ v0.2.6) will, after upgrading to
v0.2.7, **stop exposing both listeners**: the zero disables, and the UCI
options already contain the zeros. To keep using the loopback
management API / metrics after upgrading, set explicit ports:

```sh
uci set goshisen.main.api_port='8080'
uci set goshisen.main.metrics_port='9090'
uci commit goshisen
/etc/init.d/goshisen restart
```

**Metrics/Grafana impact:** a Prometheus scrape target on
`127.0.0.1:9090/metrics` (and any Grafana dashboard fed by it, e.g.
`goshisen_packets_total`, `goshisen_queue_overflow_total`,
`goshisen_flow_offload_state`) stops receiving data after the upgrade
until `metrics_port` is set explicitly. Set
`uci set goshisen.main.metrics_port='9090'` (and `api_port` if the API
is used) **before** upgrading, or right after and then restart.

A one-time `logread` warning on the first post-upgrade start (proposal
in the item 2 PR, not merged: apk `postinst` marker +
`init start()` `daemon.warn`) will name the two options and point at
these commands.

### 2. Init script: absent/empty port options are now disabled, not an abort

Previously, a UCI config **without** `api_port`/`metrics_port`, or with
them empty, made the init script abort (`goshisen: api_port '' out of
range`) so the daemon never started — forwarding stayed blocked by the
boot guard (fail-closed) but the service was down and it was loud only
in logread. In v0.2.7:

- absent/empty option → treated as `0` (listener disabled) with a
  `logread` warning naming the option;
- non-numeric / out-of-range / negative / whitespace value → start
  aborts with a `logread` error naming the option (fail-closed: the
  boot guard keeps forwarding blocked, the daemon does not start);
- the init script always renders explicit integer values, so a listener
  can never start "by accident" with a value the config meant to
  disable.

### 3. `api_host` loopback guard

The API previously accepted any `api_host` (only whitespace was
rejected), so a typo like `api_host: 0.0.0.0` silently exposed the
unauthenticated GET endpoints on the network. In v0.2.7:

- accepted loopback forms: empty, `127.0.0.1`, any `127.0.0.0/8`,
  `::1`, `localhost`;
- any other IP literal or hostname makes the daemon **refuse to start**
  unless the operator explicitly opts in with one of:
  - `allow_non_loopback_api_host: true` (config file / UCI,
    `option allow_non_loopback_api_host '1'`),
  - `GOSHISEN_ALLOW_NON_LOOPBACK_API_HOST=1` (environment),
  - `--allow-non-loopback-api-host` (flag).

### 4. Metrics listener: only `GET` (and `HEAD`) accepted

The standalone metrics listener now registers `/metrics` for `GET`
only. `CONNECT` and other methods return `405` (previously `200`, one
of the S-005 GO-2026-6613 preconditions). Prometheus scraping (`GET`)
is unchanged.

## Init failure behavior on forwarding (measured, discriminating baseline)

Re-measured 2026-11-21 on a **fresh** OpenWrt 25.12.6 x86/64 QEMU guest
(kernel `6.12.112`) whose firewall is the stock default — fw4 zones
`lan` (forward `ACCEPT`) → `wan` (forward `DROP`) with the `lan_wan`
forwarding — so the baseline is discriminating: with **no** goshisen
installed the LAN→WAN probe **passes** (`http=200`). Preparing the image
without the package is what makes this valid: an image that ever had the
package installed keeps the fail-closed `inet goshisen` chain (the boot
guard leaves it, and the daemon leaves it on stop), so "nothing
installed" would otherwise still be blocked.

Measured transitions (0.2.6-r1 and 0.2.7 test build, IPv4 + paired IPv6
on the dual-tap v6 lab; probe = LAN netns → `proof.txt`, `http=200`
pass / `000 rc=28` blocked):

| State | IPv4 | IPv6 | hook queue rule (counter) | `/proc/net/netfilter/nfnetlink_queue` |
| --- | --- | --- | --- | --- |
| no goshisen, fw4 default | **200** | **200** | no table | empty |
| daemon running, ACCEPT policy | 200 | 200 | grows | `100 …` (+ `101 …`) |
| invalid `api_port 'abc'` → abort | blocked | blocked | **grows** | **empty** (no listener) |
| service disabled (`enabled=0`) | blocked | blocked | grows | empty |
| `/etc/config/goshisen` missing | blocked | blocked | grows | empty |
| daemon killed, hook left, no respawn | blocked | blocked | grows | empty |
| daemon killed, procd respawn intact | transient block only | — | grows | refilled by respawn |

Queue-rule counter deltas per blocked state (v4 = v6, one blocked probe
per family per state): `20 → 26 → 32 → 38 → 44` (0.2.6) and
`10 → 16 → 22 → 28 → 34` (0.2.7) — i.e. the packets the LAN client
sends **do reach the goshisen queue rule** and are dropped by the kernel
because no userspace listener is bound. That is the mechanism, and it is
the goshisen table (not fw4) doing the blocking.

- **Old abort path (≤ v0.2.6):** missing/empty options → init script
  aborts (`goshisen: api_port '' out of range`); daemon never starts;
  the hook (boot guard chain, or the previous daemon's table left in
  place on stop) keeps forwarding blocked. **Measured blocked.**
- **v0.2.7:** missing/empty options → `0` (listeners disabled) **plus a
  `logread` warning**; the daemon starts and enforcement runs, so
  blocking is decided by policy alone (a `DROP` policy still blocks; an
  `ACCEPT` policy passes). An invalid value → same fail-closed abort,
  with an error naming the option.
- **Daemon death:** with procd respawn intact, the gap is bounded —
  measured `1605` probes at ~0.15 s cadence across the kill: `2` blocked,
  `1603` passed (the daemon was back before the next probe); deny probes
  never passed in any run.
- **`/etc/config/goshisen` missing (scenario v):** the init script
  refuses to start (`goshisen: service is disabled`), the pre-existing
  hook **stays**, and forwarding stays blocked until the operator
  restores the config or runs `goshisen hook cleanup`. This is the state
  a `apk del`-style cleanup fixes. Router-local access (SSH/LuCI/serial)
  is never queued, so recovery stays possible from the WAN side.
- A failure path that would block forwarding for a **remote** router is
  therefore the fail-closed abort. Mitigation: keep the service disabled
  until you are on-site, or use the serial/SSH management plane (never
  blocked by the forward hook). Full measurement:
  `docs/release/v0.2.7-upgrade-evidence.md`.

## Security advisory (S-005) recap for v0.2.5/v0.2.6 users

- v0.2.5 (and earlier v0.2.x) apk payloads embed go1.27.1; CLI
  archives go1.25.14 — 11 reachable stdlib IDs. **v0.2.6 is the toolchain
  fix** (apk payload + CLI archives go1.27.4). v0.2.7 continues that.
- The listener-defaults correction applies to v0.2.5/v0.2.6 users:
  **both loopback listeners are on whenever the service is enabled**
  (the UCI `'0'` values do not disable on those releases). After
  upgrading to v0.2.7 they are off with the packaged config. If you
  stay on ≤ v0.2.6, set `GOSHISEN_API_PORT=0` /
  `GOSHISEN_METRICS_PORT=0` in the service environment or keep
  `enabled=0`.
- Severity unchanged: Low (default; loopback-only, token-gated
  mutations, unauthenticated GETs) / Medium under a non-loopback
  `api_host` (which v0.2.7 now refuses unless opted in).

## Signing key status (F-02, out of scope for v0.2.7)

The CLI release key `GH_RELEASE_SIGNING_KEY` remains a **repo-level**
secret; the release.yml sign step is not environment-scoped. The apk
signing workflow (`apk-sign.yml`) already uses the `signing`
environment with branch policy + required reviewers. Moving the CLI
key to the environment and scoping the release.yml sign step is a
separate, maintainer-only change (issue draft in `/data/v027/f02-signing-env-issue.md`); v0.2.7 ships with the repo-level key as today.

## Known limitations (unchanged from v0.2.6)

- Kernel matrix verified: 6.12.112 on OpenWrt 25.12.6 x86/64 only.
- arm64: verified only under QEMU TCG.
- The apk is not in `checksums.txt` (different key/trust domain).
- Stateful IPv6 requires the bidirectional ESTABLISHED/RELATED rule.
- Tags remain annotated but unsigned until allowed-signers is configured
  (see `docs/release/signed-tags-plan.md`).
