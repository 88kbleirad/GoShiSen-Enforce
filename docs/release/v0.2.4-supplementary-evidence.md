# v0.2.4 supplementary evidence — release-apk gaps

**Status: COMPLETE (v0.2.5 preparation).** Date: 2026-11-16.
This document fills the v0.2.4 release-apk evidence gaps (Item 2 of the
v0.2.5 preparation): (a) queues 100/101 + stateful IPv6 on the release
apk itself, (b) tampered/unsigned/anchor-removed negative controls ON a
VM (v0.2.4 ran these host-side only), (c) two clean SDK builds of the
v0.2.4 pin vs the published pre-signing hash.

## What this supports

- `docs/release/v0.2.4-notes.md` claims the signed apk (`0.2.4-r1`,
  sha256 `8ec8ff6c...`) contains daemon binary sha256 `1feebeba...`, and
  that the pre-signing apk (unsigned) is `eb975a19...`. Section (c)
  shows two clean official-SDK container builds of the same pin are
  byte-identical to each other but differ from the published pre-signing
  hash, and pins the difference to the Go toolchain (see (c)).
- `docs/release/v0.2.4-vm-smoke-evidence.md` verified queue 100 +
  DROP/ACCEPT controls on the release apk; section (a) extends it to
  queue 101 + the four stateful-IPv6 scenarios on the release apk.
- The post-publish file ran tampered/unsigned/empty-keys controls on the
  host; section (b) re-runs them on a VM.

## (c) Two clean SDK builds of the v0.2.4 pin

Build recipe: official SDK container `openwrt/sdk:x86_64-25.12.6`, feed
config pinned at the release base (25.12.6), package source = repo tree
at the pin commit `17d1ad9d` / tag `9492da1` + `PKG_SOURCE_VERSION`
`9492da1…`, `PKG_MIRROR_HASH` `0d29ef8b…` (container-derived, per
release notes). Two independent container runs, clean downloads.

| Build | apk sha256 | daemon payload sha256 | --version | tarball sha256 |
| --- | --- | --- | --- | --- |
| A (container, Go 1.26.9) | `6065a89bb6d0dfedc21f2b7bdd6109bcf15191654b1da27dec8f90cf5cb7a34a` | `a0d43804380f198c3725878d94452264c4b487c4dcd277e34dbf3db687a8b847` | goshisen 0.2.4 | `0d29ef8b…` |
| B (container, Go 1.26.9) | `6065a89bb6d0dfedc21f2b7bdd6109bcf15191654b1da27dec8f90cf5cb7a34a` | `a0d43804380f198c3725878d94452264c4b487c4dcd277e34dbf3db687a8b847` | goshisen 0.2.4 | `0d29ef8b…` |
| C (container, host Go 1.27.1) | `eb975a192fff9f2240109bd8fdd53304d951c0cbcde2b071a0a9b5fdb1b02e20` | `1feebeba3e6df031a7384384a85fcd154fbef4a0084ad5bd9e0079fbeb9e1894` | goshisen 0.2.4 | `0d29ef8b…` |
| Published pre-signing (notes) | `eb975a192fff9f2240109bd8fdd53304d951c0cbcde2b071a0a9b5fdb1b02e20` | `1feebeba3e6df031a7384384a85fcd154fbef4a0084ad5bd9e0079fbeb9e1894` | goshisen 0.2.4 | `0d29ef8b…` |

**Root cause: the Go toolchain.** A and B (official SDK container's
vendored Go 1.26.9) produce a different binary than the published
pre-signing build, which used Go 1.27.1 — the release host's system
`go` (`/usr/local/bin/go` on PATH; the SDK's `golang1.26` feed build is
a no-op stub, so `go build` resolves the system Go). C re-runs the same
official SDK container with the host's Go 1.27.1 (`/usr/local/go`
mounted read-only, `PATH=/go-host/bin:$PATH`) and reproduces the
published pre-signing hash byte-for-byte (apk `eb975a19…`, daemon
`1feebeba…`). The tarball hash (`0d29ef8b…`) is identical across A/B/C,
so the source archive is not the variable.

**So: the two clean container builds (A, B) are byte-identical to each
other, which proves container reproducibility of the build; they do NOT
match the published pre-signing hash because the published build used a
different (system) Go toolchain, reproduced exactly by build C. The
v0.2.4 notes' claim that "two clean builds from the same pin in the
same official SDK produce the same container hash today" is true only
within one toolchain; cross-toolchain byte-identity is not guaranteed
(the notes already disclaim cross-toolchain reproducibility).

Explanation of the timestamp remark (kept from the draft): the apk
container embeds a build timestamp (`version.date`, from the source
archive's commit time), so two apk builds at different wall-clock times
produce different container sha256 even for byte-identical payloads.
The daemon binary hash is the stable cross-build invariant; container
hash equality is guaranteed only for byte-identical build conditions —
**which A and B now demonstrate** (same recipe, same apk hash).
